## 1. エグゼクティブサマリー

コードベース自体の健全性はおおむね良好だった。

- lint、Web版テスト 802件、shared のテスト 135件、各パッケージの typecheck はすべて通過した。

一方で、**構成と運用に起因する重大なリスク**が次の3系統で見つかった。

1. **Web版がブラウザから Gemini API キーを使っている（Critical）。** ビルド時に `VITE_GEMINI_API_KEY` を渡すと、そのキーが配信 JS に平文で含まれることを実証した。
2. **Gemini プロキシの防御がすべて「環境変数が設定されていれば有効」という作りになっている。** 設定漏れがあると、誰でも使える Gemini プロキシになる。さらに dev-trace 機能は、ユーザーの会話全文を30日間保存する。
3. **App Store 提出に向けたプライバシーまわりの不整合。** 「全データ削除」が実際には全データを消さない。プライバシーポリシーが実際のデータフローを反映していない。

### Critical

#### A-01【C】Web版で Gemini API キーがブラウザのバンドルに含まれる
- **場所**
  - `src/services/firebaseClient.js:54-57`：`VITE_GEMINI_API_KEY` を読み込む。
  - `src/App.jsx:585`：`x-goog-api-key` を付けてブラウザから直接 Gemini を呼ぶ。
  - `src/api/gemini.js`：同じ処理の重複実装（どこからも import されていない）。
  - `src/i18n/translations.js`：UI 文言がキーの設定を促している。
- **実証**：`VITE_GEMINI_API_KEY=AUDIT_CANARY_KEY_123 npm run build` を実行すると、`dist/assets/index-*.js` に canary 文字列がそのまま含まれていた。
- **影響**：本番ビルドにキーを入れていれば、誰でも DevTools からキーを取り出せる。第三者による無制限利用、課金の急増、クォータの枯渇につながる。
- **推奨**
  1. 直ちに Cloudflare の本番 Web ビルドの環境変数を確認する。キーが入っていれば Google AI Studio / GCP で**キーをローテーション**し、HTTP リファラ制限と API 制限を付ける。
  2. Web版もモバイル版と同じく `workers/jibunkaigi-gemini-proxy` の `/api/jibunkaigi/reply` を経由させる。`firebaseClient.js` から `geminiApiKey` を削除し、`src/api/gemini.js` も削除する。
- **工数**：M

### High

#### A-02【H】Web版の appId が Firestore ルールで拒否される
- **場所**
  - `src/services/firebaseClient.js:52`：`appId` の既定値が `'self-conf-v10'`。
  - `index.html` と `src/` のどこにも `__app_id` を注入するコードがない。
  - `firestore.rules:4-6` は `self-conf-v10-mobile(-dev)` しか許可していない。
- **影響**：Web版がモバイル版と同じ Firebase プロジェクトを使っている場合、セッション・メッセージ・プロフィールの読み書きがすべて `permission-denied` になる（保存機能が壊れている）。別プロジェクトを使っている場合は、そちらのルールが `firestore.rules` とは別管理になっており、監査の対象外になっている。
- **推奨**
  - 本番 Web の Firebase プロジェクトと、デプロイ済みのルールを確認する。
  - 同じプロジェクトなら、Web用の appId を `isAllowedAppId` に加えるか、Web版の既定値を変更する。
- **工数**：S

#### A-03【H】Gemini プロキシの認証・CORS・レート制限がすべて「未設定なら無効」
- **場所**：`workers/jibunkaigi-gemini-proxy/src/index.ts`
  - 認証：`FIREBASE_PROJECT_ID` が未設定なら `enforceFirebaseAuth` はスキップされる。
  - CORS：`ALLOWED_ORIGIN` が未設定なら `*`。
  - レート制限：`RATE_LIMIT_KV` が未設定なら無効。
  - `wrangler.toml.example` ではこれらがコメントアウトされている。
- **補足**
  - モバイル版は匿名認証（`apps/mobile/services/firebase/mobileAuth.ts`）なので、ID トークンの検証は「このアプリの利用者であること」の保証にしかならない。誰でも匿名トークンを取得して API を叩ける。
  - レート制限は IP 単位で、KV の read-then-write のため非アトミック。`CF-Connecting-IP` が無い場合は `'unknown'` という1つのバケットに集約される。
- **影響**：設定が漏れていれば、第三者が無制限に Gemini を使える（コストと濫用）。
- **推奨**
  1. 本番 Worker で `FIREBASE_PROJECT_ID`、`ALLOWED_ORIGIN`、`RATE_LIMIT_KV` が設定されていることを確認する（§5 チェックリスト）。
  2. 本番では「未設定なら起動時に 503 を返す（fail-closed）」に変える。例えば `ENVIRONMENT=production` のとき必須にする。
  3. uid（`sub`）単位の日次クォータを追加する。Firebase App Check の導入も検討する。
  4. レート制限を Cloudflare の Rate Limiting binding か Durable Object に移す。
- **工数**：M

#### A-04【H】dev-trace がユーザーの会話全文を30日間保存し、単一シークレットで全件読み出せる
- **場所**：`index.ts` の `recordTrace` / `handleDevTracesRead`、`apps/mobile/services/ai/geminiProxyClient.ts:19-20`
- **内容**
  - 保存項目：入力全文、userName、直近30件の文脈、プロンプト、出力。さらに、2回目の Gemini 呼び出しで生成した "reflection" も保存する。
  - 保存期間：TTL 30日。uid は記録せず、マスキングもしない。
  - 読み出し：`GET /api/jibunkaigi/dev-traces` が最新200件を返す。読み出しにはレート制限がかかっていない。
  - クライアント側：`EXPO_PUBLIC_DEV_TRACE_KEY` は EXPO_PUBLIC なので、**設定してビルドするとアプリバンドルに埋め込まれる**。そのビルド（preview や internal を含む）を入手した人は、30日分の全トレースを読み出せる。
  - リクエストボディの `devTraceKey` フィールドと `Authorization: Bearer <secret>` という旧経路が残っている。
- **影響**：センシティブな内省内容が漏洩しうる。プライバシーポリシーにも記載がない（A-06）。
- **推奨**
  - 本番 Worker では `DEV_TRACE_SECRET` を設定しない、または `DEV_TRACE_KV` をバインドしない。
  - 読み出しはシークレットではなく Cloudflare Access などで保護する。
  - 読み出しにもレート制限をかける。
  - 旧経路を削除する。
  - TTL を短縮する（例：7日）。
  - 収集するのは開発者本人の uid に限定する（許可リスト方式）。
  - シークレット比較は本ブランチで定数時間比較に変更済み（§6）。
- **工数**：M

#### A-05【H】モバイル版の「すべてのデータを削除」が全データを削除しない
- **場所**：`apps/mobile/services/userDataDeletion.ts:32-48`、`services/dataDeletionPlan.ts`、`components/session/MobileSessionDrawer.tsx:212-216`
- **欠落しているもの**
  1. 匿名 Firebase ユーザーを削除しない（`deleteUser` や `signOut` の呼び出しがない）。削除の直後に `onNewSession()` が同じ uid で新しいセッションを作る。
  2. 付箋・会議録（`reflectionShelfRepository` のシングルトン）をクリアしない。一方で画面文言（`dataDeletionPlan.ts:29`）は「初期化されます」と説明しており、実際の挙動と食い違っている。
  3. オンボーディング完了フラグと、メモリ上の userName をリセットしない。後で保存が走ると、旧名がプロフィールに書き戻される。
  4. 実行中の AI 応答をキャンセルしない。`useUniversalConversation.ts:406` の世代チェックを通過した応答が、削除後に `saveMessage` / `saveSession`（:437-441）で保存され、データが復活する。
  5. `sendMessage` は message を保存してから session を保存する（:369-370）。session の保存に失敗すると、親ドキュメントのない messages が残る。これは `deleteAllSessions` の列挙に引っかからず、削除されない。
  6. 起動時に匿名サインインに失敗してローカルリポジトリに fallback している場合、クラウドのデータが残っていても「成功」と表示される。
- **影響**：App Store Review Guideline 5.1.1(v)（アカウントとデータの削除）と、ユーザーへの説明の正確性に抵触するリスクがある。
- **推奨**：削除処理を `runStorageTask` のキューに直列化し、事前に進行中のリクエストを無効化する。そのうえで次を行う。
  - 付箋・会議録のリポジトリに `clearAll()` を追加する。
  - `resetOnboarding()` を呼ぶ。
  - 最後に `deleteUser(auth.currentUser)` を呼ぶ。
  - Firebase が設定済みなのにローカル fallback 中の場合は、失敗として扱う。
  - 可能なら、Cloud Functions / Admin SDK による uid 配下の再帰削除に置き換える。
- **工数**：M

#### A-06【H】プライバシーポリシーとアプリ内の説明が、実際のデータフローを反映していない
- **場所**：`privacy-policy.md`、`apps/mobile/data/legalContent.ts:23-29`

  - 処理委託先（Cloudflare、Google）
  - 保存期間
  - 越境移転（個人情報保護法 第28条）

- **工数**：M（法務確認を含む）

## 4. データフローとプライバシーポリシーの差分

```
[モバイル] ──匿名Auth──▶ Firebase Auth
    │  ├─ Firestore: artifacts/{appId}/users/{uid}/sessions/*, messages/*, profile/settings
    │  └─ AsyncStorage: user-profile(名前), onboarding フラグ, Firebase の認証状態（平文）
    └─ HTTPS ──▶ Cloudflare Worker (gemini-proxy)
                   ├─ IP → RATE_LIMIT_KV（TTL 120秒）
                   ├─ 入力・名前・文脈・出力 → DEV_TRACE_KV（TTL 30日, 有効時のみ）
                   ├─ エラー本文・出力の断片 → Cloudflare Logs
                   └─ プロンプト（入力・名前・文脈） → Google Gemini API
[Web] ──匿名Auth──▶ Firebase（appId 不一致, A-02）
    └─ ブラウザから直接 Google Gemini API（A-01）
```

| 項目 | 実際の挙動 | ポリシーの記載 | 対応 |
|---|---|---|---|
| 会話・名前を Gemini に送信 | あり（Worker 経由、Web は直接） | 一部あり（名前の送信は記載なし） | 追記 |
| Cloudflare を処理委託先として利用 | あり | なし | 追記 |
| dev-trace（全文を30日保存） | 設定次第であり | なし | 本番で無効化するか、記載する |
| IP アドレスの利用 | レート制限のキー | なし | 追記 |
| サーバーログ | Gemini のエラー本文や出力の断片 | なし | 記載するか、ログを縮小する |
| 保存期間 | Firestore は無期限、KV は上記 | なし | 追記 |
| 越境移転 | 米国などの事業者を利用 | なし | 追記（個人情報保護法 第28条） |
| 全データ削除 | 不完全（A-05） | 「削除できる」と記載 | 実装を直すか、記載を正確にする |
| 日付・連絡先 | — | プレースホルダ | 記入する |
